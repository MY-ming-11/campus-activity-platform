# 抢名额压测报告

## 一、测试目标

验证一件事：**并发抢名额时不会超卖**。

具体来说，100 个名额、1000 个人同时抢，最终必须精确地只有 100 个人成功，数据库里只有 100 条报名记录，Redis 余量必须归零且不为负。

## 二、测试环境

| 项 | 配置 |
|---|---|
| 压测机 / 服务机 | 同一台本机（Windows），未做任何隔离 |
| JDK | Dragonwell 21.0.11 |
| 后端 | Spring Boot 3.2.5 内嵌 Tomcat，默认 200 个工作线程 |
| MySQL | 8.0.45，本机 |
| Redis | 7.x，本机 |
| 连接池 | HikariCP 最大 20 连接 |

说明：压测客户端和服务端跑在同一台机器上，两边抢 CPU，所以延迟数据偏悲观。真实部署到服务器上会更好看一些，但**这组数字的意义在于一致性验证，不在于性能上限**。

## 三、测试方法

压测程序在 [benchmark/SignupBenchmark.java](../benchmark/SignupBenchmark.java)，零依赖，JDK 21 单文件直接跑：

```bash
java benchmark/SignupBenchmark.java http://localhost:8080 1000 100
```

程序做的事：

1. 用管理员账号新建一个活动，名额 100
2. 准备 1000 个压测用户（`bench_0` ~ `bench_999`，密码统一 `bench123456`）
3. 用 `CountDownLatch` 卡住所有用户，等到齐后同时发车
4. 每个用户对同一个活动发起一次报名请求
5. 等待消息表消费完，读取活动最终余量

**并发模型用 Java 21 虚拟线程。** 同样是 1000 并发，平台线程要预分配约 1GB 栈内存，虚拟线程只在真正阻塞时挂起，内存开销可以忽略。这不是为了压测才用的技巧，Java 21 项目里这就是默认选择。

## 五、结果分析

### 为什么 P50 有 567ms

这个数字看着不漂亮，但拆开看很合理：Tomcat 默认只有 200 个工作线程，1000 个并发请求里，同时只有 200 个在真正处理，剩下 800 个在排队。**P50 的 567ms 里绝大部分是排队时间，不是处理时间。**

接口自身的处理路径是：校验活动 → Redis Lua 原子预扣 → 写一条消息表记录 → 返回，没有数据库查询、没有跨服务调用。Redis 的 Lua 脚本本身是亚毫秒级的。

如果要压低延迟，方向是明确的：调大 Tomcat 线程数、或者把写消息表这一步也异步化。这次没有做，是因为**压测要验证的是一致性，不是性能上限**。为了把数字做好看而加一堆优化，反而会掩盖真实瓶颈。

### 900 个售罄请求说明什么

1000 个人抢 100 个名额，900 个人收到"名额已经抢完了"。关键点在于：**这 900 个请求都没有写数据库。**

如果不用 Redis 预扣，这 900 个失败请求会全部打到 MySQL 上——先查余量、发现没了、返回失败。1000 个并发查询里 900 个是无效查询，数据库白白扛了 9 倍的压力。

Redis 预扣把"判断能不能抢到"这件事挪到了内存里，数据库只承接真正成功的 100 次写入。这是这套方案最实在的收益。

### 限流为什么没触发

限流是**按用户**计的（令牌桶容量 5，每秒补 1 个），而这次每个用户只发了一次请求，所以 0 次触发，符合预期。

单独验证过：同一个用户连续快速点 10 次报名，前 5 次放行（1 次真报名 + 4 次幂等返回"你已经报名过"），第 6 到第 10 次全部返回 429。限流和幂等这两层是叠加工作的——限流挡住机器刷接口，幂等挡住真实用户的手抖重复点击。

## 六、这次压测没能证明的事

如实记录，避免把报告写得比事实好看：

- **没有验证多实例部署下的一致性。** 当前是单机单实例，Redis 是唯一的共享状态。多实例下这套方案依然成立（因为原子性在 Redis 侧），但没有实测。
- **没有做长时间稳定性测试。** 只跑了一次突发流量，没有验证持续压力下的内存和连接池表现。
- **没有对比开关 Redis 预扣的性能差异。** "Redis 预扣能减轻数据库压力"这句结论是从请求路径推导出来的，没有做 A/B 实测。
- **消息表积压情况没有专门统计。** 这次只有 100 条待落库消息，200ms 一批、每批 200 条，一轮就消费完了，看不到积压。

## 七、如何复现

```bash
# 1. 启动后端
cd backend && mvn spring-boot:run

# 2. 跑压测（在项目根目录）
java benchmark/SignupBenchmark.java http://localhost:8080 1000 100

# 3. 核对数据库（把 <活动id> 换成报告里输出的 id）
mysql -uroot -p -e "
  USE activity_platform;
  SELECT COUNT(*), COUNT(DISTINCT user_id) FROM activity_signup WHERE activity_id = <活动id>;
  SELECT status, COUNT(*) FROM quota_outbox WHERE activity_id = <活动id> GROUP BY status;"

# 4. 核对 Redis
redis-cli GET activity:stock:<活动id>
redis-cli SCARD activity:users:<活动id>

# 5. 清理压测数据
mysql -uroot -p < sql/cleanup-benchmark.sql
```
