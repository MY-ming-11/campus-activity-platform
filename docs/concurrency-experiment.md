# 高并发报名的一致性与性能对比实验

## 一、实验目的

活动名额是典型的「有限资源 + 高并发争抢」场景：一场 100 个名额的活动，可能有一千多人同时点报名。如果不做并发控制，超卖几乎是必然的。

本实验实现三种主流的并发控制方案，在完全相同的条件下压测，回答两个问题：

1. 三种方案能否都保证不超卖？
2. 它们的性能差多少，差在哪里？

## 二、三种方案

三套实现都在 `backend/src/main/java/com/luosh/activity/service/strategy/` 下，实现同一个接口 `SignupStrategy`。限流、活动校验、返回结构完全一样，只有并发控制手段不同——这样测出来的差异才能归因于方案本身。

### 方案一：数据库悲观锁

```sql
SELECT id FROM activity WHERE id = ? FOR UPDATE;   -- 锁住活动行
SELECT COUNT(*) FROM activity_signup WHERE activity_id = ? AND status <> 'CANCELED';
-- 判断名额后插入报名记录
```

同一活动的所有报名在这把行锁上排队，完全串行。实现最简单、正确性最容易论证，代价是吞吐被串行化。

### 方案二：数据库乐观锁

不加锁，靠两句原子语句：

```sql
INSERT IGNORE INTO activity_signup (activity_id, user_id, ...) VALUES (?, ?, ...);
UPDATE activity SET occupied = occupied + 1 WHERE id = ? AND occupied < quota;
```

唯一索引挡住同一用户的重复提交，条件更新挡住名额超卖。数据库对同一行的 UPDATE 本身就是串行的，把 `occupied < quota` 放进 WHERE 就不会突破上限。

**这里有个顺序问题值得单独说**：必须「先插报名记录、再扣减」。如果反过来先扣减，同一用户并发双击时两次扣减都会成功，但唯一索引只留下一条报名记录，`occupied` 就虚高了——名额凭空变少。先插入的话第二次请求在唯一索引上就失败了，根本走不到扣减那一步。而「扣减失败」的情况直接抛异常让事务回滚，刚才插入的记录会一起撤销，不需要手写补偿逻辑。

### 方案三：Redis 预扣 + 本地消息表异步落库

名额的权威值放在 Redis，用 Lua 脚本把「查重 + 判断余量 + 扣减」三步做成一个原子操作：

```lua
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return {2, stock} end  -- 已报名
if stock <= 0 then return {1, 0} end                                          -- 已满
stock = redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return {0, stock}
```

扣减成功后只写一条「待落库」消息，真正的报名记录由后台每 200ms 消费一批写入。数据库只承接成功的那 100 次写入，900 次失败请求根本不碰数据库。

## 三、测试方法

压测程序在 `benchmark/SignupBenchmark.java`，用 Java 21 虚拟线程承载并发用户：

```
java SignupBenchmark.java <服务地址> <并发用户数> <名额> <策略>
```

每次运行的流程：新建一场活动（名额 100）→ 准备 1000 个用户 → 用 `CountDownLatch` 让所有人卡在同一起跑线 → 同时发车 → 统计结果 → 等落库完成后核对数据库。

策略通过请求头 `X-Signup-Strategy` 传给后端，需要服务端开启 `signup.allow-override`。这样三种方案能在同一个 JVM、同一个数据库上连续跑，外部条件完全一致。

### 一个必须避开的测试陷阱

最初压测程序跑在宿主机上，通过 Docker Desktop 映射的端口访问服务，1000 并发时出现了大量 `ConnectException`（连接被拒）。排查过程：

1. 后端日志里一条 ERROR 都没有，说明不是业务异常
2. 把 Tomcat 的 `accept-count` 从默认的 100 调到 1000，问题依旧，说明不是 Tomcat 的接受队列
3. 把压测程序放进 Docker 网络内直接访问 `backend:8080`，异常降为 0

结论：**瓶颈是 Docker Desktop 的端口转发**，它在 1000 个连接同时建立时拒绝了一部分。这是测试环境的限制，不是三个方案的差异。所有正式数据都在容器网络内测得。

这个坑本身也值得记下来——压测时「客户端报错」未必是服务端的问题，**先把测试工具自身的瓶颈排掉，再去解读数据**。

## 四、测试环境

| 项 | 配置 |
|---|---|
| 机器 | 单个开发机，压测程序与服务端在同一台机器 |
| 后端 | Spring Boot 3.2.5，Tomcat 线程池 200，HikariCP 最大 20 连接 |
| MySQL | 8.0，容器内 |

## 五、实验结果

1000 个用户抢 100 个名额：

| 策略 | 抢到 | 售罄 | 异常 | 总耗时 | 吞吐 | 平均延迟 | P50 | P90 | P99 |
|---|---|---|---|---|---|---|---|---|---|
| Redis 预扣 | 100 | 900 | 0 | 204 ms | **4901 req/s** | 92 ms | 94 ms | 116 ms | 147 ms |
| 悲观锁 | 100 | 900 | 0 | 1782 ms | 561 req/s | 1319 ms | 1368 ms | 1634 ms | 1693 ms |
| 乐观锁 | 100 | 900 | 0 | 1667 ms | 599 req/s | 1304 ms | 1350 ms | 1561 ms | 1604 ms |

数据一致性核对（直接查库）：

| 活动 | 策略 | 名额 | 有效报名数 | 去重用户数 | 超卖 |
|---|---|---|---|---|---|
| id=17 | Redis 预扣 | 100 | 100 | 100 | 无 |
| id=18 | 悲观锁 | 100 | 100 | 100 | 无 |
| id=19 | 乐观锁 | 100 | 100 | 100 | 无 |

三种方案都精确地只有 100 条报名记录、100 个不同的用户。**没有超卖，没有重号。**

## 六、结果分析

### Redis 方案快在哪里

吞吐是另外两个方案的 8 倍以上，延迟差了十几倍。原因不是 Redis 比 MySQL 快，而是**它让 900 个注定失败的请求根本没走到数据库**：

| 方案 | 打到数据库的写请求 |
|---|---|
| Redis 预扣 | 100 次（只有成功的） |
| 悲观锁 | 1000 次（每个请求都要先开事务、加锁、统计） |
| 乐观锁 | 1000 次（每个请求都要先尝试插入） |

1000 并发里有 900 个是来晚了的人，他们的结果早就注定了。Redis 在内存里就判掉了这 900 个，数据库的压力直接降到十分之一。

### 乐观锁为什么没有比悲观锁快

这是本次实验最有意思的发现。乐观锁理论上没有锁竞争，应该明显快于悲观锁，但实测两者几乎一样（599 vs 561 req/s，差 7%）。

原因在**连接池**：两个方案都在事务里持有数据库连接，而 HikariCP 的最大连接数是 20。这意味着不管用哪种并发控制手段，同一时刻最多只有 20 个请求在真正执行，其余全在等连接。

**锁竞争还没来得及成为瓶颈，连接池已经先成了瓶颈。**

这个结论对实际开发有直接指导意义：优化并发性能时，要先确认瓶颈在哪一层。如果连接池只有 20，把行锁换成乐观锁带来的收益几乎为零；反过来，把连接池调大之后，乐观锁的优势才可能显现出来。凭直觉选「更先进」的方案，往往会优化错地方。

### 三者的适用场景

| 方案 | 适用 | 不适合 |
|---|---|---|
| Redis 预扣 | 瞬时高并发抢购、对响应时间敏感 | 要求强一致、不能容忍异步窗口 |
| 悲观锁 | 并发量不高、逻辑复杂、正确性优先 | 高并发，会迅速成为瓶颈 |
| 乐观锁 | 冲突较少（是「改」不是「抢」）、想避免长事务 | 冲突激烈时大量重试，反而更慢 |

## 七、本实验的局限

如实记录，避免过度解读数据：

- **压测程序和服务端在同一台机器上**，两者抢同一份 CPU，绝对数值偏悲观。有意义的是三者的相对差距。
- **只测了 1000 并发这一档**，没有做并发量从小到大的曲线，看不出拐点在哪里。
- **每一档只跑了一轮**，没有多次取样取平均，也没有算标准差。
- **连接池固定为 20**，没有做「调大连接池后乐观锁是否反超」的补充实验——这是最值得继续做的一个方向。
- **没有测长时间稳定性**，只测了一次突发流量。

## 八、复现方式

```bash
# 1. 启动服务，并打开策略覆盖开关（仅实验用，生产环境关掉）
SIGNUP_ALLOW_OVERRIDE=true docker compose up -d --build

# 2. 在 Docker 网络内跑压测（不能从宿主机跑，见第三节的测试陷阱）
#    把最后的 redis 换成 pessimistic 或 optimistic 即可测另外两种
docker run --rm --network activity-platform_default \
  -v "$PWD/benchmark:/bench" -w /bench \
  maven:3.9-eclipse-temurin-21 \
  java SignupBenchmark.java http://backend:8080 1000 100 redis

# 3. 核对数据库，valid_signups 必须恰好等于名配额
docker compose exec mysql mysql -uroot -p -e "
  USE activity_platform;
  SELECT a.id, a.quota, COUNT(s.id) AS valid_signups, COUNT(DISTINCT s.user_id) AS users
  FROM activity a
  LEFT JOIN activity_signup s ON s.activity_id = a.id AND s.status <> 'CANCELED'
  WHERE a.title LIKE '压测活动%'
  GROUP BY a.id, a.quota;"
```
